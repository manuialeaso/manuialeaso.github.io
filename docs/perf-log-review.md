# 日誌排版批次優化驗證

## 結果

`afk-perf.js` 已將三個日誌頻道的更新整理為「先完成所有 DOM 寫入，再讀取所有高度，最後設定捲動位置」。固定三頻道輸入的 5 組瀏覽器比較中，排版次數每輪都從 **720 次減為 240 次，減少 66.7%**；訊息內容、次序、保留上限、使用者捲動鎖定及最後位置完全相同。

這是日誌更新的局部改善。隔離測試的耗時中位數由 4,482.5 毫秒降至 4,021.2 毫秒，約少 10.3%；其中 2 組新版較慢，顯示共享環境的時間量測有波動。這份結果不代表整體遊戲 FPS 提升 10.3%，也不能據此把原本 profile 中的 16.5 秒日誌熱點全數扣除。

## 為什麼修改這裡

16 人隊伍、法利昂、4 倍 CPU 降速的前景 CPU profile 中，`flushOne` 自耗時為 16,512.862 毫秒，包含子呼叫約 16,686.22 毫秒。其 11,413 次取樣中，7,510 次落在 `scrollTop = scrollHeight` 所在行；這支持優先處理同步排版，而不是重建日誌節點或刪減訊息。

舊版依序對每一頻道執行「加入訊息 → 裁剪舊訊息 → 讀高度 → 捲到底部」。若三個頻道都有訊息，前一個頻道讀高度時剛完成排版，下一個頻道的 DOM 寫入又讓排版失效。

新版保留每個頻道原本的加入及裁剪操作，只將自動捲動分成兩個集中步驟：全部頻道的 DOM 寫入結束後讀高度，再設定各自的 `scrollTop`。單一頻道更新仍需要原本那一次排版。

## 保留的行為

- 訊息 HTML、顏色、來源標籤、分類及每個頻道內的次序相同。
- 戰鬥／系統／世界的一般保留上限仍為 50／50／60；向上捲動鎖定後仍為 150／150／200。
- 頻道鎖定判斷仍在原本的位置進行；鎖定時不強制捲到底部。
- 未被裁剪的 DOM 節點保持原物件，因此既有文字選取、按鈕焦點得以保留。
- 前景 200 毫秒後排入下一幀、背景 250 毫秒的既有排程與佇列上限未改；未開 `perf-render` 的原有逐幀排程也未改。
- 稀有掉落的未讀提示仍立即更新；快轉補跑仍不新增日誌。
- 缺少元素、單一頻道高度讀取或捲動設定拋錯時，其他頻道仍可繼續更新。

本次正式程式修改只有 `afk-perf.js` 的日誌 `flushOne`／`flushAll` 區段，沒有變動戰鬥、產生日誌的來源、其他 UI 或 CSS。

## 驗證方法

執行：

```sh
node scripts/test-perf-log.mjs
node scripts/test-perf-log.mjs --browser
```

原版日誌區塊凍結於 `scripts/fixtures/perf-log-baseline.js`；新版從目前的 `afk-perf.js` 擷取。原始完整檔案 SHA-256 為 `553e7900b3ef3d745184fe233319f30e81eab4abbe7360e281181de40206f1e2`。

### 語義檢查

12 項 VM 檢查全部通過，涵蓋 HTML 與來源、次序、上限、保留節點、鎖定切換、缺少／隱藏元素、單頻道例外、未讀提示、前景／背景排程、停用開關，以及排程和入列原始碼逐字相同。另明確驗證新版所有 DOM 寫入都先於高度讀取，所有高度讀取都先於捲動設定。

真實 Chromium 使用專案原生的日誌、捲動鎖定與切換頻道函式。原版及新版各使用全新頁面，以下 9 種情境的完整訊息 HTML、數量、捲動高度／位置、鎖定狀態與提示樣式逐項完全相同：

| 情境 | 驗證重點 |
| --- | --- |
| 一般追加訊息 | 50／50／60 上限與自動到底部 |
| 使用者向上捲動後追加 | 原選取節點與文字保留，捲動位置仍為 80 |
| 鎖定時超過上限 | 150／150／200 上限，沒有強制回到底部 |
| 原生「回到底部」 | 解除鎖定並恢復一般上限 |
| 訊息中的按鈕取得焦點 | 原節點持續連接，焦點不遺失 |
| 隱藏系統頻道後追加 | 保持隱藏，照常接收訊息 |
| 原生切換回系統頻道 | 未鎖定頻道正確回到底部 |
| 稀有掉落尚未 flush | 未讀提示立即更新 |
| 稀有掉落完成 flush | 訊息及順序與原版一致 |

### 隔離量測

使用 5 組原版／新版配對，逐組交替先後順序。每一次量測均建立全新的瀏覽器 context 及頁面；不使用路由攔截，也不載入戰鬥或外部資源。

頁面設置三個 310 × 150 像素的可捲動日誌區，保留既有的 `contain: content`。先對每頻道暖機輸入 200 則，再開始量測 **240 批 × 每批 12 則 × 3 頻道**，每批執行一次 flush。三頻道同時可見，持續有訊息且未鎖定。訊息內容及 HTML 結構固定。

量測時手動固定 flush，捕捉但不執行日誌自動計時器，避免計時器穿插影響配對；這部分測的是更新函式本身，排程等價由前述語義測試單獨證明。讀取 Chrome DevTools Protocol 的 `LayoutCount`、`LayoutDuration`、`RecalcStyleCount`、`RecalcStyleDuration`、`TaskDuration` 差值。每組也比對最後完整 HTML、數量、捲動位置／高度及鎖定狀態。

## 適用範圍與限制

排版次數由 3 降為 1 的結果，適用於同批有多個可見且自動捲動頻道更新的情況。實際遊戲經常只顯示一個日誌分頁，其他頻道隱藏，或使用者已鎖定捲動；這些情況的收益會較小，不能直接套用本次三頻道測量比例。

這次沒有重新執行完整隊伍的計時效能 A/B，因此沒有新的整體 FPS、主執行緒總時間或電量結論。保留既有訊息量及使用行為是本次邊界；時間結果顯示局部改善方向，穩定且直接的證據是五輪排版／樣式重算次數一致減少，以及所有訊息與操作狀態比對通過。
