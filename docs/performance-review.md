# 遺物戰鬥效能檢討

測試日期：2026-10-22（UTC）。這份報告評估遺物來源查詢與事件派發的 CPU 改善；完整通關與反傷結論另見 [戰鬥平衡報告](relic-balance-review.md)。數據來源為 [正式比較資料](relic-performance-results.json)，本次量測的程式差異保存在 [效能差異補丁](relic-performance-delta.patch)。

## 結論與適用範圍

GM 道具同時帶入 250 種遺物來源時，重複整理來源、篩選派發對象，以及為沒有對應效果的事件預先建立輔助資料，是明確的 JavaScript 熱點。移除這些重複工作後，兩個 GM 情境的 480 次 tick 合計耗時下降約 **54%–58%**；前景整個量測期間的 Chromium `ProcessTime` 下降約 **44%–49%**。所有來源與原有觸發順序仍保留。

16 人隊伍的 tick 合計耗時也下降約 **27%–44%**，但前景畫面的戰鬥紀錄與版面讀取仍佔用大量時間。4 倍 CPU 降速時，整段 `ProcessTime` 只下降 **2.83%／4.49%**，且法利昂案例的實際等待時間略增。這兩個數字不足以宣稱多人畫面已全面流暢。

兩個 GM 案例在 4 倍降速後的 tick p95 仍為 **296.4／331.3 毫秒**，高於 100 毫秒的原生戰鬥步進間隔。這次修正降低 CPU 成本，沒有證明低階實機不會卡頓，也沒有測得真實手機的 FPS、耗電或溫度。

## 比較方法

使用 [原生效能測試程式](../scripts/test-relic-performance.mjs)，每個案例、每個降速倍率各開一個全新的瀏覽器 context 與頁面。量測環境為 Linux x64、Node 24.19.0、Chromium 133.0.6943.0、1280 × 900 視窗；容器暴露 9 個邏輯 CPU，主機 CPU 型號為 AMD EPYC 9V74。4× 指 Chrome DevTools Protocol 的 CPU 降速，不等同特定手機機型。

前後版本取自同一份 2026-10-22 14:29:47 UTC 凍結快照，只有以下三檔不同：

- `afk-relic-runtime.js`：來源快取及派發清單。
- `afk-relic-defense.js`：沒有對應 handler 的事件提早返回；只在使用時讀武器標籤與低血條件。
- `afk-relic-weapons.js`：沒有對應 handler 的事件提早返回。

其餘每個檔案的 SHA-256 完全一致，完整指紋保存在 JSON。快照以本機 HTTP server 直接送出，沒有使用 Playwright request interception，避免路由攔截本身污染效能。正式前景測量期間為 14:58:33–15:17:46 UTC，前後兩組分開執行，未同時跑其他長時間壓測。

每次都執行 **480 次原生 tick，共 48 秒遊戲時間**，固定種子為 `20261022`。前景模式 `state.ff=false`，沿用每 100 毫秒安排一次 tick、原生死亡結算與 `flushTickRender`；原生動畫、VFX、UI interval 與 rAF 保持運作。只停止原本的戰鬥／存檔自動時鐘，避免同時存在第二條戰鬥時鐘。若一個 tick 太慢，實際完成時間就會延長，不會減少 tick 數或略過戰鬥效果。

稀疏工作目錄沒有完整圖片、音效和字型資產，兩版本均以 CSP 阻擋這些請求。實際 JS 與 DOM 更新保留，但這仍是 headless／軟體 GPU 環境，無法代表完整資產在裝置上的繪製與解碼成本。

## CPU profiler 找到的熱點與對應修正

採用約 1 毫秒取樣的 Chromium CPU profiler，表中為函式自己的取樣時間，不含子函式；取樣本身有誤差，僅用於定位成本。

| 熱點與情境 | 修正前 → 修正後 | 實作 |
|---|---:|---|
| GM 99999／1×，防具 `dispatch` | 6,128 → 1,315 毫秒 | 沒有 handler 的事件直接返回；稀疏事件只準備真正有該效果的物品 |
| GM 99998／1×，防具 `dispatch` | 8,167 → 1,849 毫秒 | 同上，並把武器標籤與低血條件改為需要時才計算 |
| GM 99999／1×，runtime 派發 | 舊外層 1,629＋逐來源 callback 7,846 → 新迴圈 3,101 毫秒 | 清單與武器頻道視圖依來源向量快取；移除每事件重複 filter／literal 陣列 |
| 16 人法利昂／1×，`sourceList` | 1,253 → 262 毫秒 | 比對欄位 ID，不再每次排序、串接整串裝備簽章 |
| 16 人法利昂／4×，`sourceList` | 4,324 → 1,193 毫秒 | 同上，保留原地換裝、欄位移除、新增及 invalidate 的失效條件 |
| 16 人林德拜爾／1×，`sourceList` | 1,194 → 207 毫秒 | 同上 |

來源快取仍保留同名來源去重、較高階版本選擇與 catalog 排序；裝備物件原地修改也會被發現。派發視圖只快取「哪些來源收到事件」，不保存傷害、治療、機率或當下角色狀態。GM 每次普通攻擊的各武器頻道，以及整包只觸發一次的防具分支，仍遵守原來的範圍與順序。

模組提早返回只適用於原本沒有 handler 的事件。防具的少量專屬事件已逐一對照：夥伴能力 #152／189／241／245、隊友受傷 #155／186、仇恨 #153／154／184、DOT 前置 #139、DOT 後置 #143；+0 的 #163 受傷前效果也保留。武器標籤只在 #137 的相應分支讀取，低血判定只在 #172 的相應分支讀取。

### 尚存的前景成本

優化後 16 人法利昂／4× 的 `afk-perf.js` `flushOne` 自身取樣時間仍約 **16.51 秒**，林德拜爾／4× 約 **13.47 秒**。法利昂同場的 `getBoundingClientRect` 與 `innerText` 讀取也分別約佔 4.69 秒、2.55 秒。這是後續戰鬥紀錄／DOM 工作的具體檢查方向。

本報告的 A/B 沒有改 `afk-perf.js`，也沒有包含後續投射物 transform、字級或紀錄刷新優化；若這些功能另作修改，應以自己的匹配 A/B 評估，不能把本報告的百分比相加。

## 語義一致性：另外做完整原生重播

前景視覺效果與戰鬥共用 `Math.random`。動畫排程改變時，視覺效果可能先消耗不同數量的亂數，即使種子及 tick 數相同，前景戰鬥細節也不保證逐筆相同。因此前景數據用來量負載；**是否維持原有戰鬥語義，另外用同步原生重播驗證**。

重播仍呼叫真實 tick、傷害、技能、怪物與遺物模組，採 `state.ff=true` 並停止視覺計時器，使戰鬥亂數消耗可確定。前後兩份快照各跑相同 480 tick：

| 情境 | 遺物模組 callback 數 | 傷害／受傷／治療事件數 | 亂數呼叫數 | 前後結果 |
|---|---:|---:|---:|---|
| GM 武器 99999／安塔瑞斯 | 11,883,462 | 36,724 | 94,159 | 一致 |
| GM 防具 99998／巴拉卡斯 | 14,571,214 | 46,142 | 120,857 | 一致 |
| 16 人／法利昂 | 742,625 | 4,720 | 23,219 | 一致 |
| 16 人／林德拜爾 | 767,049 | 4,780 | 22,575 | 一致 |

合計 **27,964,350 次 callback、92,366 筆觀測到的傷害與治療事件**。逐一比較的內容包含：完整傷害／治療觀測資料列及順序、每個 tick 的 callback／事件順序摘要、逐來源事件次數、HP／MP／怪物狀態、亂數狀態，以及最後完整戰鬥結果。四場完整事件列均逐位元組相同；所有 tick 摘要與最終語義 SHA-256 也一致，完整值保存在 JSON。

早期尚在調整 harness 的一次重新載入／攔截請求試跑，曾出現 GM 防具案例中間摘要不同，但事件次數、每 tick 戰果、最終狀態及亂數相同；未建立其原因，原始紀錄保留並未納入正式結論。其後三次完整事件重播一致，最終改用直接 HTTP 的四場正式重播亦全部一致。沒有用那次異常數據宣稱等價或計算效能改善。

## 重現方式

完整快照與 CPU profiles 位於測試工作目錄 `../work/performance/`；每份前景 JSON 記錄對應 `.cpuprofile` 檔名。新一輪測試可先用 `--capture` 另存快照，再用 `--snapshot` 指向前後兩份凍結檔案。請先比對 manifest，只讓預定要測的檔案不同。

```sh
node scripts/test-relic-performance.mjs --snapshot ../work/performance/base --mode foreground --rates 1,4 --out ../work/performance/server-baseline-foreground.json
node scripts/test-relic-performance.mjs --snapshot ../work/performance/optimized --mode foreground --rates 1,4 --out ../work/performance/server-optimized-foreground.json
node scripts/test-relic-performance.mjs --snapshot ../work/performance/base --mode audit --trace-events --out ../work/performance/server-baseline-audit.json
node scripts/test-relic-performance.mjs --snapshot ../work/performance/optimized --mode audit --trace-events --compare ../work/performance/server-baseline-audit.json --out ../work/performance/server-optimized-audit.json
node scripts/test-relic-dispatch-cache.mjs
```

下一輪效能工作應先保留這些行為與順序檢查，再針對已量到的前景紀錄刷新／版面讀取成本做匹配比較。降低模擬頻率、減少來源、吞掉觸發或縮短測試工作量，都不能當作同一玩法的優化成果。
